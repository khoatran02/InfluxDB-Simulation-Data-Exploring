# InfluxDB Benchmarks: Write Throughput, Storage Footprint, and Query Latency

Generated by `benchmarks/benchmark.py` (raw data: `reports/benchmark-results.json`). To re-run:
`uv run --env-file .env python benchmarks/benchmark.py --runs 5 --query-runs 50`

To run the concurrency load test:
`uv run --env-file .env python benchmarks/concurrent_requests.py --concurrency 500`

## 1. Concurrency & Load Testing
A load test simulating hundreds of simultaneous IoT devices sending data at the exact same millisecond. 
Using `ThreadPoolExecutor` and Python's standard `urllib` to bypass third-party library overhead.

| Metric | Result |
| --- | --- |
| Total concurrent requests | 500 |
| Success Rate (HTTP 204) | 500/500 (100.0%) |
| Total Execution Time | 0.272 seconds |
| API Throughput | 1837.9 requests/s |
| Min Latency | 7.27 ms |
| Median Latency (p50) | 13.16 ms |
| 95th Percentile (p95) | 20.54 ms |
| 99th Percentile (p99) | 22.67 ms |
| Max Latency | 26.30 ms |

**Conclusion:** InfluxDB handled the simultaneous burst of 500 requests flawlessly, achieving sub-30ms latency even for the slowest requests under high concurrent load.

## 2. Write Throughput and Storage Size
Each run wrote into a **new temporary bucket** (deleted afterward). Writes were synchronous (`SYNCHRONOUS`), measuring only the send and server ACK time (excluding line protocol creation). 5 runs per configuration.

| Dataset | Points | Batch Size | Median (points/s) | Min–Max (points/s) | Median Storage (Bytes) | Bytes/point |
| --- | --- | --- | --- | --- | --- | --- |
| Original CSV (37,922 rows, 37,920 valid) | 37,920 | 100 | 7,124 | 6,948–7,994 | 36,721,673 | 968 |
| | | 500 | 14,027 | 14,007–14,344 | 37,078,764 | 978 |
| | | 1000 | 16,529 | 16,294–16,632 | 37,454,044 | 988 |
| | | 5000 | 28,161 | 25,774–29,032 | 37,920,491 | 1000 |
| Synthetic 80k (82,000 rows) | 82,000 | 100 | 6,900 | 6,883–6,978 | 41,346,708 | 504 |
| | | 500 | 14,001 | 13,901–14,109 | 42,112,677 | 514 |
| | | 1000 | 16,526 | 16,306–17,565 | 42,806,715 | 522 |
| | | 5000 | 27,129 | 26,408–27,716 | 43,990,168 | 537 |

Reference: Line protocol 11,566,260 B (original), 25,198,992 B (80k); 80k CSV is ≈ 82,001 rows.

**Observations:** Write speed increases ~4x from batch 100 to 5000, tapering off afterward. Batch 5000 reaches ~27–28k points/s.

> [!WARNING]
> Storage was measured using `du -sb` on the `engine/data/<id>` + `engine/wal/<id>` directories immediately after writing (waiting 2 seconds), without final compression/compaction. The size **hardly scales with point count** (36.7 MB → 41.3 MB when points increase by 2.16x), meaning most of it is fixed overhead (pre-allocated WAL/index), not true TSM size. Do not use Bytes/point as a compression ratio metric. For accurate measurements, you must wait for a snapshot/compaction (default `cache-snapshot-write-cold-duration` is 10 minutes) or use a significantly larger dataset.

## 3. Query Latency: Mean vs Max
Queried the same bucket, same time window (the entire dataset), `temperature` field, using `aggregateWindow(createEmpty: false)`. Measured on the client side using `time.perf_counter()` wrapping the `query_api.query()` call until results were fully consumed. Discarded the first 5 warmup runs, followed by **50 measured runs**; p95 calculated via linear interpolation.

| Dataset | Window | Function | Result Rows | Median (ms) | p95 (ms) | Max (ms) |
| --- | --- | --- | --- | --- | --- | --- |
| Original | 1h | mean | 2,163 | 27.5 | 46.6 | 52.1 |
| Original | 1h | max | 2,163 | 26.6 | 39.1 | 49.2 |
| Original | 1d | mean | 101 | 16.7 | 18.6 | 29.2 |
| Original | 1d | max | 101 | 16.7 | 17.9 | 25.3 |
| 80k | 1h | mean | 6,606 | 55.2 | 89.5 | 91.4 |
| 80k | 1h | max | 6,606 | 52.9 | 87.6 | 89.1 |
| 80k | 1d | mean | 286 | 24.3 | 25.3 | 45.4 |
| 80k | 1d | max | 286 | 24.1 | 25.4 | 40.0 |

**Conclusion against the 100 ms target:** All 8 configurations comfortably succeeded (highest p95 was 89.5 ms, max 91.4 ms), though the safety margin for the 80k dataset with a 1h window narrowed to ~10%. The difference between `mean` and `max` is negligible; latency depends primarily on the point count and the number of returned result rows. Note: This is on a single machine, localhost, sequential queries, without concurrent read load.
